# Native PDF Signing

Kinetic now supports a standard electronic-signature workflow directly in the platform. Qualified electronic signatures (QES) remain provider-backed.

## Capability

For standard signing requests:

- Signable documents are PDF-only.
- The task opens in the dedicated `/signature-tasks/:recipientId` workspace, outside the normal dashboard shell.
- Kinetic generates the signature from the recipient's official employee/user profile. Example: `Mark Warunge` becomes `M.Warunge`.
- The recipient chooses a visual signature style, gives explicit electronic-signature consent, and submits.
- The signing timestamp is generated by the backend. The signing date is not accepted from the browser.
- Each recipient owns one signature field and one date field.
- Sequential and parallel multi-signatory workflows use the existing recipient routing model.
- Completed values are rendered into a final PDF and stored as a `signed_document` `SignatureArtifact` with a SHA-256 checksum.
- The source document remains unchanged and is retained as the `original_document` artifact.

## Field placement modes

When an administrator creates a standard request, there are two options.

### Signing record page

This is the default. Kinetic appends one or more electronic-signing record pages and positions each signatory's signature/date block automatically. Each record page supports up to eight signatories in a two-column, four-row layout.

### Place fields on PDF

The administrator selects each signatory and places one signature field and one date field directly on the uploaded PDF. Coordinates are stored as normalized top-left values (`0..1`) so the browser and PDF renderer use the same field model.

## Main API additions

- `GET /api/signature-requests/recipients/:recipientId/document` — current native signing PDF, including completed signatures and signing-record pages.
- `POST /api/signature-requests/recipients/:recipientId/submit` — records explicit consent and submits the server-generated signature.
- `GET /api/signature-requests/recipients/:recipientId/signed-document` — final signed PDF after all required signatories have completed.

The legacy `PATCH .../sign` route remains for compatibility, but client-supplied `signature_name` is ignored. Identity and signing time are authoritative server values, and legacy actions are recorded with the separate `legacy-sign-action-v1` consent version rather than the new checkbox-consent version.

## Data model

Migration `023_native_pdf_signing` adds:

- `SignatureRecipient.signature_method`
- `SignatureRecipient.signature_style`
- `SignatureRecipient.consented_at`
- `SignatureRecipient.consent_version`
- `signature_fields` table with recipient ownership, page number, normalized geometry, required flag, value and completion timestamp.

## PDF implementation

Frontend PDF rendering and field placement use `pdfjs-dist`. Backend PDF stamping uses `pypdf` and ReportLab. Rotated source pages are normalized before server-side overlays are merged so field coordinates remain aligned with the PDF viewer.

The signing engine intentionally does not attempt to edit DOCX/XLSX layouts. General Documents may still contain those formats, but native signing requires PDF.

## Evidence and audit behavior

At request creation, Kinetic captures the immutable original document artifact and validates its SHA-256 checksum. Each recipient signature event records the server timestamp, consent version, generated signature method/style, and source-document checksum. When the final recipient signs, Kinetic renders and stores the final PDF and records its checksum on the completion event.

QES requests continue through the configured Dropbox Sign/eID provider path and are not submitted through the native signing endpoint.

## Deployment

Install the updated backend dependencies and run the database migration:

```bash
cd backend
pip install -r requirements.txt
flask db upgrade
```

Install the updated frontend dependencies and build:

```bash
cd frontend
npm ci
npm run build
```

`pdfjs-dist` 6.2.108 requires Node.js 22.13+ (or 24+); the frontend package engine has been updated accordingly.

## Verification

The implementation includes `backend/app/tests/test_native_signature_workflow.py` covering:

- generated identity (`Mark Warunge` -> `M.Warunge`), consent and authoritative timestamp;
- automatic signing-record fields and final signed artifact;
- two parallel signatories with separate signature/date fields placed directly on one PDF page;
- final PDF containing both generated signatures.

Run the normal suites in a fully provisioned development environment:

```bash
cd backend
pytest

cd ../frontend
npm test
npm run build
```
